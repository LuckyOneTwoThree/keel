## 〇、v3 → v3.0 变更摘要

| 维度 | v3（archive） | v3.0（本文件） |
| --- | --- | --- |
| 上线策略 | 一次性 push 15 件设施 + 两周复审 | pull-based，只发 6 项，其余 deferred 摩擦拉动 |
| 设计哲学 | agent 中心化（agent 是主要执行者） | PM 中心化（PM 是主要执行者，agent 是可选加速器） |
| 地基约束 | 3 条 | **4 条**（新增"节点自给自足"） |
| 草稿区 | agent 起草必经 | agent 起草时用，PM 直写不经 |
| 确认门 L2 | 针对所有写入 | 仅针对 agent 写入，PM 自己写无需确认 |
| 触发规则 | 需 daemon（桌面端跑不起来） | 降级为"会话开始重聚简报" |

| frontmatter | 与 prose 双写 | 正文不重复 frontmatter 字段 |

| schema 版本 | 双版本共存 | 一次性迁移，不留老规则分支 |

**v3.0 仍守的三条地基约束**：① 单一真相源 ② 记忆层只追加不回改，推翻只改状态字段 ③ AI 最小权限四条。

## 一、设计哲学

### 1.1 第四条地基约束：节点自给自足

> **每个文件、每个阶段都可独立存在与操作。agent 是连接器，不是必经路径。关联是软的，节点是硬的。**

这是 v3.0 最核心的修正。它否定了 v3 的隐性假设"agent 是主要执行者，PM 在环确认"。正确的表述是：

| 设施 | v3 假设 | v3.0 修正 |
| --- | --- | --- |
| SOP | 流程定义，PM 走流水线 | 协助菜单，PM 任选或全跳过 |
| REQ 主线 | 流程必经脊椎 | 软关联脊椎，可事后补 |
| 草稿区 | agent 起草必经 | agent 起草时用，PM 直写不经 |
| 确认门 L2 | 针对所有写入 | 仅针对 agent 写入 |
| 派生层 | agent 刷新 | agent 不刷新时仍存在（stale 但不消失） |

**关键原则：关联 ≠ 依赖。**

- 需求池（登记册）↔ PRD：关联（PRD 引用 REQ 编号），但 PRD 可独立存在（没立 REQ 也能写，事后补编号）
- PRD ↔ 方案：关联，但方案可独立存在
- 决策 ↔ 需求：关联，但决策可独立存在
- 行动项 ↔ 决策：关联，但行动项可独立勾选完成

agent 可帮串联（"你这个 PRD 还没立 REQ，要帮你补一个吗？"），但不强制。**PM 永远可以先做后补、或不补。**

### 1.2 pull-based 上线策略

> 新增设施必须证明它减少的 agent 摩擦 > 它引入的维护负担。**且只在真实摩擦出现后才上线，不预建。**

v3 的"两周复审"是 push-based（先建再砍）。v3.0 改为 pull-based：只发"不上就没法干活"的 6 项，其余标 deferred + 拉动条件，由真实摩擦触发上线。

## 二、v3.0 最小集（6 项必发）

> 这 6 项是"不上就没法干活"的。每项含 v3 红队反馈的修法。

### 2.1 frontmatter schema（修 A1：正文不重复字段）

**为什么必发**：check.py 校验的物理基础。prose 字段下所有强制机制都是空话。

**A1 修法**：v3 把状态/关联等字段同时写在 frontmatter 和 prose 里（双事实源缩到一条目内）。v3.0 改为**正文不重复 frontmatter 字段**：

```markdown
---
id: REQ-0007
type: req
title: 用户登录双因子认证
date: 2026-07-25
status: 待评审
scope: 在范围
related: [DEC-0012, RSK-0003, DEP-0002]
review_due:        # 仅 dec/rsk 用
---

### REQ-0007 — 2026-07-25
用户登录双因子认证

正文只放散文（背景/描述/影响），字段全在 frontmatter。
`### 编号 — 日期` 保留作人读锚点，但状态/关联/范围等字段全部上提。
```

**条目级 frontmatter 字段集**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | 编号，如 REQ-0007 |
| type | 是 | req/prg/dec/com/kb/rsk/dep/gkb |
| title | 是 | 一句话标题 |
| date | 是 | ISO YYYY-MM-DD |
| status | 是 | 见状态枚举 |
| scope | req 专用 | 在范围 / 明确不做 |
| related | 否 | 关联编号列表 |
| review_due | dec/rsk 专用 | 复审到期日 |

**状态枚举**（check.py 强制）：

| 类型 | 允许状态 |
| --- | --- |
| REQ | 待评审 / 开发中 / 已验收 / 已砍 |
| PRG | 进行中 / 已完成 / 已阻塞 |
| DEC | 评估中 / 生效 / 已推翻→DEC-XXXX / 待复审 |
| COM | 已对齐 / 待跟进 / 失效 |
| KB | 本地 / 已晋升→GKB-XXXX / 过时 |
| RSK | 开放 / 已缓解 / 已关闭 |
| DEP | 等待中 / 已就绪 / 已逾期 |
| GKB | 生效 / 已归档 |

> **通用例外状态**：所有类型均可追加 `已作废(PM拒绝)` 或 `已作废(误)→(指向)`，用于回滚与勘误。不计入"活跃条目"过滤。

### 2.2 git 版本层（修 C1、C2）

**为什么必发**：审计、回滚、并发根因一次性解决。

**C1 修法**：**"agent 写盘即 commit"设为硬 SOP**。pre-commit 只在 commit 时触发，非 git 路径回退到自觉。所以 agent 每次写真相源必须立即 commit，不许批量积压。PM 直写时建议每次也 commit（但不强制，PM 自己负责）。

**C2 修法**：**commit trailer `Approved-by`**。git 记 who wrote 不是 who approved；agent 提交则 blame=agent。L2 写入必须带 trailer：

```
[REQ-0007] 新增需求

Approved-by: PM
Reviewed-by: agent
```

或条目 frontmatter 加 `confirmed_by: PM` 字段。两者择一，前者更轻。

**commit 规范**：

```
[<编号>] <动作短语>

Approved-by: PM   # L2/L3 写入必带；PM 自写可省

例：
[REQ-0007] 新增需求

Approved-by: PM
```

**写入原子性**：一条条目 = 一个 commit。单条目状态变更不得跨 commit（防半成品状态）。

**派生文件冲突**：现状.md / INDEX.md 冲突时重跑派生即可，不必上锁、不必 merge。

**基线文件冲突**：章程 / 需求登记册范围 / 路线图里程碑——走 L3 确认门串行化，天然不冲突。

### 2.3 check.py 校验（修 C3：唯一性硬阻断，连续性仅警告）

**为什么必发**：把"约定"变"强制"。没有它，所有编号协议、状态枚举、frontmatter schema 都是自觉。

**C3 修法**：v3 把"编号=max+1"设为硬阻断——一条历史坏数据会阻断全局。v3.0 改为：

| 校验项 | 规则 | 失败动作 |
| --- | --- | --- |
| 编号唯一 | 同前缀编号全局唯一 | **硬阻断** |
| 编号连续 | 新编号建议 = max+1 | **仅警告**（遇 gap 不阻断） |
| 悬空引用 | related 中每项必须存在 | 硬阻断 |
| 状态枚举 | 必须命中枚举 | 硬阻断 |
| frontmatter schema | 必填字段齐全、类型正确 | 硬阻断 |
| 日期格式 | ISO YYYY-MM-DD | 硬阻断 |
| 排序 | 同文件内倒序（最新在顶） | 警告 |
| 双写检测 | 同一信息不在两处真相源 | 警告（启发式） |

**落地**：`scripts/check.py` + `.git/hooks/pre-commit` 调用。agent 写入前先跑一次自检（不必走 git），失败则不落盘、回报 PM。

### 2.4 草稿区 `.draft/`（修 A3：幂等键从意图派生）

**为什么必发**：宪章第 1 条"所有写入先出稿"，但 v2/v3 没有物理位置。agent 起草 PRD/周报/方案无处可去。

**A3 修法**：v3 用 `draft-{uuid}.md`——uuid 随机，agent 崩溃重启后认不出自己上次的草稿。v3.0 改为**幂等键从操作意图派生**：

```
draft-req-0007-prd.md          # 起草 REQ-0007 的 PRD
draft-weekly-2026-07-25.md     # 起草 2026-07-25 周报
draft-dec-0013.md              # 起草 DEC-0013
draft-req-0007-方案.md          # 起草 REQ-0007 的方案
```

或维护 `.draft/tasks.yaml` 清单（每个草稿一行 `id / intent / created_at / status`）。

**规则**：

- 位置：项目根 `.draft/`（可选 gitignore，或纳入 git 作审计）
- 生命周期：起草 → PM 审 → 确认后 rename/移动到正式位 → 清空草稿
- 拒绝：PM 拒绝 → 直接删（草稿区不享受只追加保护）
- 幂等：草稿文件存在 = 工作流断点；agent 重启后扫 `.draft/` 按文件名识别意图续传
- **PM 直写不经草稿区**——草稿区仅服务于 agent 起草

### 2.5 agent会话.md（短时记忆层）

**为什么必发**：性价比最高。没有它 PM-agent 协作不能跨会话延续——会话断/重启后 agent 一脸懵。

**位置**：`记忆/agent会话.md`（append-only，享受只追加保护）

**模板**：

```markdown
### SESSION-2026-07-25-1430 — 2026-07-25
- 项目: PROJ-灯塔
- 目标: 起草 REQ-0007 PRD
- 已做: 读 REQ-0007 登记册条目 + DEC-0012；起草 PRD 到 .draft/draft-req-0007-prd.md
- 卡在: PRD §4 验收标准未定，等 PM 给验收清单
- 下一步: PM 给验收清单 → 补 PRD → 落 01-需求/REQ-0007-PRD.md
- 相关: REQ-0007, DEC-0012
```

**规则**：

- 每次会话**结束前**写一行（agent 主动写，PM 不必手填）
- 每次会话**开始时**先读最近 3 条 SESSION-，恢复上下文
- 仅记"工作流状态"，不记"项目事"（项目事归 PRG/DEC/COM）
- 不作真相源，但享受只追加（防 agent 误删历史会话）

### 2.6 现状.md 分节写 + 重聚简报（修 A2、B1）

**为什么必发**：没有它 agent 会抹 PM 手填的 §1；桌面端无触发机制。

#### A2 修法：分节写，禁止整文件覆盖

v3 写"覆盖式写现状.md（§1 PM 手填保留）"——自相矛盾。v3.0 改为**按节定位 + 替换该节内容，不动其他节**：

```
现状.md 结构（### 二级标题作分隔符）：
  # 现状（项目驾驶舱）
  ## 1. 本周焦点          ← PM 手填，agent 永不触碰
  ## 2. 当前里程碑        ← agent 派生
  ## 3. 当前阻塞与待办    ← agent 派生
  ## 4. 到期复审提醒      ← agent 派生

agent 刷新规则：
  - 按 `## N.` 定位节
  - 只替换 §2-§4 的内容
  - §1 永不触碰（即使为空也不写）
```

派生失败兜底：数据缺失时显示 `(待补: 引用 X)`，不留空字段。

#### B1 修法：触发规则降级为"重聚简报"

v3 §十六 "P0 立即提醒""DEP T-3 天提醒""静默超 24h 升级"——需 daemon，桌面端跑不起来。v3.0 改为**会话开始重聚简报**：

```
每次 agent 会话开始 → 跑一次"重聚扫描"
输出："你上次离开后（<最后会话时间>），这些到期了："
  - [P0] RSK-0003 仍开放，已 3 天
  - [到期] DEC-0012 复审到期 2 天
  - [T-3] DEP-0002 期望交付 2026-07-28，剩 3 天
PM 决定是否处理。
```

把"实时告警"改成"重聚简报"——会话制下唯一诚实的做法。agent 不在时系统照常运行，agent 在时给快照。

**更新协议**（§1 vs §2-§4 分工）：

| 字段 | 更新方 | 触发时机 |
| --- | --- | --- |
| §1 本周焦点 | PM 手填 | 周一或里程碑切换 |
| §2 当前里程碑 | agent 派生 | 路线图变更时 |
| §3 阻塞与待办 | agent 派生 | RSK/DEP/DEC 变更后 |
| §4 到期复审 | agent 派生 | 每次会话开始扫一遍 |

## 三、读取策略（修 C4：按状态读）

**C4 修法**：v3 §十二 "只读最近 30 天"会漏掉超期仍开放的老条目——一个 40 天前开、至今开放的 RSK 会被静默漏掉，agent 却自信地给不全答案。v3.0 改为**按状态读**：

| 数据类型 | 读取规则 |
| --- | --- |
| 真相源（REQ/RSK/DEP/DEC） | **按状态读**：状态 ∈ {开放/待评审/评估中/等待中/待复审/进行中} → 无视时间，必读；状态 ∈ {已关闭/已验收/已生效/已完成} → 仅最近 30 天 |
| 记忆类文件（PRG/COM/KB） | tail 读最近 50 条 或 最近 30 天（取小） |
| 派生文件 | 全读（文件本身不大） |

需要更早的 → grep + 按需 Read 单条目。

## 四、确认门与单写者不变式（修 B2）

### 4.1 确认门四级（L0-L3）

| 级别 | 操作 | agent 行为 | PM 行为 |
| --- | --- | --- | --- |
| L0 只读 | 读任何真相源文件 | 直接做，无需确认 | 直接做 |
| L1 起草 | `.draft/` 写草稿、刷新派生文件（现状 §2-§4） | 直接做，事后告知 PM | 不适用（PM 直写正式位） |
| L2 写真相源 | 写 REQ-/DEC-/RSK-/DEP-/PRG-/COM-/KB-/GKB- 条目 | **PM 确认编号 + 内容后落盘** | 直接写，无需确认 |
| L3 改基线 | 改章程 / 需求登记册范围 / 路线图里程碑 | **PM 显式授权 + 走 DEC-** | 直接写（但建议走 DEC- 留痕） |

**关键修正**：L2 确认门**仅针对 agent 写入**。PM 自己写无需确认——这是"节点自给自足"的体现。

### 4.2 单写者不变式（修 B2）

**B2 修法**：v3 §十五 摆出多角色并发，但 git 不是运行时锁，同一工作目录下两 agent 同时写就 last-writer-wins。v3.0 声明**单写者不变式**：

```
v3.0 不变式：
  所有真相源写入经 main_agent 串行化
  prd_agent / ops_agent / checker_agent 是"逻辑角色"（未来 contract.yaml 里的权限边界），
  不是"并发实例"（实际运行时不会同时跑）
  实际运行时 = 单个 main_agent 串行调度

多角色并发 → deferred（见 §七）
```

**与解耦的关系**：单个 PM + 单个 main agent，没有协调成本。你的"项目之间有关联但可单独执行"正是单写者不变式的体现：同一时刻只在一个项目里写，不会跨项目并发。

## 五、强制力三层诚实分层（修 B3）

**B3 修法**：v3 假装 contract.yaml 声明式 SOP 会被 agent 严格执行。实际桌面 agent 把 yaml 当 prompt 上下文读，不会"执行"。v3.0 诚实标注三层强制力：

| 层 | 机制 | 强制力 | 失败时 |
| --- | --- | --- | --- |
| L1 建议层 | AGENTS.md（人读 + prompt） | 软（模型可能不遵） | 行为漂移 |
| L2 提示层 | PM 审视（确认门） | 中（PM 纠偏） | PM 拒绝 |
| L3 强制层 | check.py（确定性校验） | 硬（阻断 commit） | 阻断 |

**不要假装 L1 能替代 L3**。contract.yaml 是给 agent 的"说明书"，check.py 是"门卫"。两者互补，不等价。

**v3.0 不发 contract.yaml**（标 deferred）。先靠 AGENTS.md（人读） + check.py（强制）跑通。agent 行为漂移严重时再上 contract.yaml。

## 六、勘误与回滚

### 6.1 勘误模式（append-only 下纠错）

> agent 写错了不能删。新增条目状态标"作废→指向正确条目"。

```markdown
---
id: DEC-0013
status: 已作废(误) → DEC-0014
date: 2026-07-25
---

### DEC-0013 — 2026-07-25
（保留原内容，不删）
```

这是只追加原则的标准应用，不是新机制。在 `写入协议.md` 里"勘误模式"一节显式写出即可。

### 6.2 基本回滚（PM 拒绝 agent 写入后）

**v3 修正**：v3 写"git revert + 在原条目追加状态"——但 revert 后条目从文件消失，PM 翻文件看不到"曾写过+被拒"的痕迹。v3.0 改为**保留条目 + 改状态 + 新 commit**（这是基本款，覆盖 90% 场景；更复杂的协议化回滚见 §七 deferred）：

```
agent:
  1. 不删原条目，将其 status 改为 "已作废(PM拒绝)"
  2. （可选）追加一行 "拒绝原因: ..."
  3. git commit [编号] 状态:作废(PM拒绝)
```

**为什么不 git revert**：revert 让条目从 markdown 文件消失，审计要靠 git log 才能还原。改状态则 markdown 自身就是审计层。

**禁止**：手工删行、`git reset --hard`、`git push --force`、`git revert`（除非 PM 显式要求且接受审计层迁移到 git log）。

**草稿区例外**：`.draft/` 下的草稿被拒绝 → 直接删（草稿区不享受只追加保护）。

## 七、deferred 清单（靠摩擦拉动）

> 以下设施 v3.0 不发，标 deferred。每个有"拉动条件"——条件满足才上线。

| 设施 | v3 原级别 | 推迟理由 | 拉动条件 |
| --- | --- | --- | --- |
| contract.yaml 机读契约 | P1 | B3：被读而不遵，先靠 AGENTS.md + check.py | agent 行为漂移严重，PM 反复纠偏同一类错误时 |
| 多 agent 角色边界 | P2 | B2：单写者不变式够用 | 真出现多 agent 并发需求 |
| 触发规则静默期 | P2 | B1：需 daemon，已降级为重聚简报 | PM 真的被重聚简报打扰时 |
| 工作区现状.md | P2 | A4：派生扇出未解决 | 跨项目数 ≥3 且 PM 真需要全局视图时 |
| `.meta.md` 机读缓存 | P2 | A4：与现状.md 双写风险 | 单项目文件量爆 context 时 |
| 行动项派生视图 | P1→降 P2 | 可先用 DEC/COM 里的 checkbox | 行动项散落难追踪时 |

| 字段级敏感标记 | P3 | D1：注意力控制非安全 | 真有敏感数据进文件时 |
| gen-index 脚本 | P3 | grep 够用 | INDEX 真的高频需要时 |

**A4 派生扇出的临时解**：v3.0 不发工作区现状/.meta，只保留现状.md。若真要上多派生层，先定规则：

```
单次派生 pass + 优先级链：
  1. 一次真相源变更 → 触发一次完整派生 pass（刷新 .meta + 现状 + 工作区现状）
  2. 若 pass 未完成（agent 中断）→ 以 .meta.updated 为准，其余标 stale
  3. 读取优先级：.meta（最新）> 现状.md（可能 stale）> 工作区现状.md（最易 stale）
  4. stale 文件头部显示 "⚠ 数据可能滞后，最后刷新: <时间>"
```

## 十·五、基础架构（继承 v2，v3.0 未变动）

> v3.0 只在 v2 基础上加"最小强制机制 + 短时记忆"。以下 v2 核心架构全部保留，详细执行规则分散落到 `PM工作宪章.md`/`AGENTS.md`/`写入协议.md`，本节仅作索引。

### 10.5.1 三段式结构

| 段 | 目录 | 职责 | 唯一性 |
| --- | --- | --- | --- |
| 共享层 | `_共享/` | 宪章、AI 契约、写入协议、通用知识 | 全局唯一一份 |
| 模板层 | `_模板/` | 项目骨架母版，克隆用 | 只读母版 |
| 项目层 | `项目/PROJ-X/` | 每个项目一份独立实例 | 逐项目隔离 |

两级归档消歧义：项目内 `归档/` = 活跃项目的月度过程收口；顶层 `已结项/` = 整个项目下线后连实例搬入。

### 10.5.2 知识双层 + 晋升机制

| 层 | 位置 | 存什么 | 编号 |
| --- | --- | --- | --- |
| 本地知识 | `项目/PROJ-X/记忆/知识库.md` | 带上下文的踩坑/临时结论 | `KB-0005` |
| 全局知识 | `_共享/知识库/全局知识库.md` | 去上下文、可复用的方法论 | `GKB-0012` |

**晋升流（PM 决定，AI 至多提示）**：本地记"事件" → 人工验证为通用规律时去上下文提炼上抬 → 全局沉淀为 GKB-，本地 KB- 状态改为 `已晋升→GKB-XXXX`（不复述内容）。这是"原料→成品"关系，不是同内容存两遍，不违反单一真相源。

### 10.5.3 统一编号 Schema

前缀 + 4 位序号，各类独立递增（per-project 作用域）。跨项目用 `REQ-0007@PROJ-灯塔`，check.py 默认不校验跨项目。

| 类型 | 前缀 | 归属文件 |
| --- | --- | --- |
| 需求（主线） | `REQ-` | `项目管理/需求登记册.md` + `文档库/01-需求/REQ-XXXX-PRD.md` |
| 进度 | `PRG-` | `记忆/进度日志.md` |
| 决策 | `DEC-` | `记忆/决策记录.md` |
| 沟通 | `COM-` | `记忆/沟通记录.md` |
| 本地知识 | `KB-` | `记忆/知识库.md` |
| 风险 | `RSK-` | `项目管理/风险登记册.md` |
| 依赖 | `DEP-` | `项目管理/依赖登记册.md` |
| 全局知识 | `GKB-` | `_共享/知识库/全局知识库.md` |

刻意不加：`ASM-` 假设流（与风险/决策重叠，折入决策"假设前提"字段）；`TODO-`（与只追加哲学冲突，行动项散在 DEC/COM 的 checkbox）。

### 10.5.4 需求追溯主线（REQ-，软关联脊椎）

以 `REQ-` 作对象型主键，串起需求的完整生命周期。**关联是软的，节点是硬的**——PRD 可独立存在（没立 REQ 也能写，事后补编号）：

```
REQ-0007 (一个需求/特性)
   ├── 触发决策    DEC-0012
   ├── 产出方案    文档库/03-方案/REQ-0007-方案.md
   ├── 关联原型    原型/REQ-0007-v2/
   ├── 引发风险    RSK-0003
   ├── 涉及依赖    DEP-0002
   └── 验收结果    文档库/05-验收/REQ-0007.md
```

只给真实特性编号，琐碎任务不占 REQ-。

### 10.5.5 项目管理域：基线 vs 控制面

同在 `项目管理/`（不建子目录，仅逻辑标注），按变更频率区分写入模式：

| 归类 | 文件 | 写入特征 |
| --- | --- | --- |
| 基线（定了少变） | 项目章程（含成功指标/北极星）、需求登记册（含范围 in/out） | 一次立好，变更须走 DEC- |
| 控制面（持续更新） | 路线图、风险登记册、依赖登记册、干系人矩阵 | 覆盖式更新当前状态 |

### 10.5.6 域边界与写入规则

- **沟通记录(COM-)反空壳**：只记干系人对齐结论、表态/立场、非正式承诺；每条必带"结论或影响"，纯 FYI 不入账。正式会议 → `06-会议`；产生决策 → `DEC-`；交付承诺 → `DEP-`；干系人身份 → `干系人矩阵`。
- **文档库两层编号段**：`01-05 阶段产出`（需求/调研/方案/评审/验收，按 `REQ-XXXX-*` 命名，一次性产出）；`06-07 周期记录`（会议/报告，按日期命名，持续累加）。
- **需求三件套边界**（互不复述，靠 `REQ-` 串联）：
  - `项目管理/需求登记册.md` — 总账/索引（编号·标题·状态·范围·关联）
  - `文档库/01-需求/REQ-XXXX-PRD.md` — 单个需求详情（PRD·用户故事·需求侧验收标准）
  - `文档库/03-方案/REQ-XXXX-方案.md` — 解决方案/技术设计
- **记忆月度分片**（可选·防臃肿）：默认单文件即可，不预先分片；仅当某日志过大影响阅读时按月起新文件，旧月滚入项目内 `归档/`。
- **原型追溯**：目录按 `原型/REQ-XXXX-vN/` 归类，在 `路线图`/`现状` 引用。
- **INDEX 检索层**：不作为手工维护常驻文件，日常检索用 grep + 需求登记册；需要跨类全景时由脚本按需生成（标"可重建·非真相源"）。

## 十三、TL;DR

- **v3 → v3.0 的核心修正**：① push-based → pull-based（只发 6 项，其余 deferred）② agent 中心化 → PM 中心化（立"节点自给自足"第四条地基约束）。
- **第四条地基约束**：每个文件、每个阶段都可独立存在与操作。agent 是连接器，不是必经路径。关联是软的，节点是硬的。PM 永远可以先做后补、或不补。
- **v3.0 最小集 6 项**：frontmatter（正文不重复字段）+ git（写盘即 commit + Approved-by）+ check.py（唯一性硬阻断连续性警告）+ 草稿区（幂等键从意图派生）+ agent会话.md + 现状.md 分节写（触发降级为重聚简报）。
- **读取策略**：按状态读——开放/活跃项无视时间必读，已关闭项仅最近 30 天。
- **确认门**：L2 仅针对 agent 写入，PM 自己写无需确认。单写者不变式——所有写入经 main_agent 串行化。
- **强制力三层**：L1 建议（AGENTS.md）+ L2 提示（PM 审视）+ L3 强制（check.py）。不假装 L1 能替代 L3。
- **deferred 11 项**：每个有拉动条件，靠真实摩擦触发上线。
- **永久砍**：多 agent 并发、触发 daemon、schema 双版本、来源标记每条、时间戳全局到分钟、最后写入者胜全局规则。
- **不动**：三段式、REQ- 软关联主线、单一真相源、只追加、AI 最小权限——这套底子对 PM + agent 协作是友好的，v3.0 只在其上加"最小强制机制 + 短时记忆"。
